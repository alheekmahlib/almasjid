# خطة إصلاح خطأ Null Check عند تعطل خدمات الموقع

## السبب الجذري (تم التحقق منه)

عند فتح التطبيق وخدمات الموقع معطلة (إذن ممنوح سابقًا + بيانات مخزنة + الجهاز متصل):

1. `GeneralController.onInit` → `initLocation` → `_activateLocation` (`general_controller.dart:222-261`).
2. السطر 239 ينفذ `getPositionDetails()` الذي يستدعي `Geolocator.getCurrentPosition` (`location_helper.dart:112`) بدون حماية → يرمي `LocationServiceDisabledException`.
3. `_activateLocation` فيه `try/finally` فقط (بدون `catch`) → الاستثناء يتخطى السطرين 251-252 → **`initializeStoredAdhan` (تحميل كاش 30 يومًا) لا يُنفذ أبدًا** → `state.prayerTimes == null` وحقول `late` في `adhan_state.dart:21-23` غير مهيأة.
4. الاستثناء يُبتلع في `initLocation` (سطر 214-215) بمجرد log.
5. أي موضع `!` غير محمي لاحقًا ينفجر بـ "Null check operator used on a null value".
6. سباق إضافي يفسر التقطع: `InternetConnectionController.isConnected` يبدأ `false`؛ إن نفّذ `initLocation` قبل تحقق حالة الاتصال يعمل المسار الاختصاري للـ offline ويُحمَّل الكاش بلا خطأ، وإلا ينفجر المسار المتصل.

القبلة سليمة التصميم أصلًا (تعتمد `PrayerCacheManager.getStoredLocation()` عبر `qibla_controller.dart:56-64, 90-106`) ولا تحتاج سوى تحصين موضع واحد.

## القرارات المعتمدة من المستخدم

- إصلاح جذري + تحصين شامل لكل مواضع الـ null-check المكتشفة.
- عند تعطل الخدمات: التطبيق يعمل من الكاش **بصمت تام** (لا رسائل ولا بطاقات).

## التغييرات

### 1. الجذر — `lib/core/services/location/location_helper.dart`

- في `getPositionDetails()` (سطر 50):
  - فحص مبكر `Geolocator.isLocationServiceEnabled()`؛ إن كانت معطلة → `log` فقط و`return` بدون رمي (الموقع يبقى كما استُعيد من التخزين).
  - تغليف استدعاء `Geolocator.getCurrentPosition` (سطر 112-125) بـ `try/catch`: عند `LocationServiceDisabledException` أو أي فشل/مهلة → `log` وreturn بأمان.
- في الـ getter `currentLocation` (سطر 197-204): جعله `LatLng?` — يُرجع المخزون من `CURRENT_LOCATION` (بقراءة null-safe للمفاتيح `latitude`/`longitude`) أو `_currentLocation` القابل للـ null، **وحذف `_currentLocation!`** (الـ setter لا يُستدعى أبدًا فالفرع الحالي قنبلة مؤكدة).

### 2. ضمان عدم تخطي تحميل الكاش — `lib/presentation/controllers/general/general_controller.dart`

- في `_activateLocation` (سطر 222-261):
  - تغليف `getPositionDetails()` بـ `try/catch` خاص بحيث يستمر التنفيذ دائمًا إلى `initializeStoredAdhan(newLocation: effectiveLocation)` أياً كانت نتيجة جلب الموقع (الحساب `effectiveLocation = pos != null ? ... : stored` الموجود أصلاً يتكفل بالاحتياط).
  - توسيع شرط `shouldUseStoredOnly` (سطر 233) ليشمل تعطل الخدمات: `(!isConnected || !(await LocationHelper.instance.isLocationServiceEnabled())) && stored != null` — يزيل الاعتماد على سباق الاتصال.
- في `updateLocationAndPrayerTimes` (سطر 345-401):
  - السطر 346: التعامل مع `currentLocation` الجديد القابل للـ null (المقارنة `newLocation != currentLocation` تظل صحيحة).
  - السطر 355: `Get.context!.showSearchBottomSheet(Get.context!)` → قراءة `final ctx = Get.context;` والتحقق من عدم الـ null قبل العرض (نفس سلوك زر التحديث الحالي لكن بأمان).

### 3. تحصين القبلة — `lib/presentation/qibla/controller/qibla_controller.dart`

- السطر 68: `mapController.value.move(userLocation.value!, 18)` → قراءة `userLocation.value` في متغير والتحقق من null قبل `move` (زر crosshair في تبويب الخريطة).

### 4. تحصين التسلسل — `lib/presentation/prayers/controller/prayers_notifications/extensions/prayer_times_serialization.dart`

- في `AdhanState.toJson()` (سطر 8): حارس في المقدمة — إذا كان `prayerTimes == null || sunnahTimes == null` → إرجاع `Map` فارغة بدل قراءة حقول `late` غير مهيأة (يمنع `LateInitializationError` من مسار `savePrayerData`).

### 5. تحصينات جوارية صغيرة (نفس عائلة الخطأ)

- `adhan_state.dart:101`: `prayerNameList[index]['sharedAdjustment']!` → `['sharedAdjustment'] ?? ''` (الدالة `getAdjustmentByPrayerName` لديها فرع default يعيد 0).
- `prayers_noti_ui.dart:112`: `receivedAction.displayedDate!` → `displayedDate ?? DateTime.now()`.
